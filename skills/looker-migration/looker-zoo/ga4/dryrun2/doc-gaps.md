## B. Misleading or wrong

- **M1** `nested-data.md:39-43`: "Port it as an EXISTS semi-join, which also keeps parent measures unduplicated (Looker gets the same result through symmetric aggregates)." This is false when the parent PK is non-unique (here, PDT-internal duplication). Looker's symmetric aggregates dedup those duplicates, EXISTS doesn't. Following it literally gives a different number in the Host-filtered state. (Highest wrong-number risk in the docs.)
- **M2** `gotchas.md:143` says "No CLI to start the Notebook Agent (`hex thread` is list/get only)", which contradicts `SKILL.md:213`, `build-notebook-agent.md:208` and `build-generative-app.md:102` (`hex thread create`). It's stale and could make an agent wrongly fall back to the native build.
- **M3** `lookml-semantics.md:332` gives the example `SELECT … FROM {{shared_df}}`. Hex dataframe SQL references a dataframe by bare name, as far as I know. Jinja braces would render the dataframe object. Worth verifying.
- **M4** `lookml-semantics.md:257`: the `N days` row gives only a lower bound (`>= DATE_SUB(CURRENT_DATE(), INTERVAL N-1 …)`), with no upper bound or timezone. It's fine for `<= now` data but loses the half-open `[start, start+N)` form Looker emits, and the tz point from §3.
- **M5** `lookml-semantics.md:44`: "parity is **exact**… a gap is a bug (unless a PDT snapshot is in play)" doesn't account for nondeterministic ties (gap 5) or incremental drift, both present here.

## C. Doc guidance that prevented a mistake I would otherwise have made

1. `lookml-semantics.md` §5:193-199 ("Which joins fire": every CASE branch, `fields: []` and empty `sql: ;;` holders) + `liquid.md:24-29` (CASE vs Jinja if). I would have ported `audience_trait` as a Jinja `if/elif`, dropped the 9 attribution joins, and missed Looker's OR-join fan-out on Tile 1. It also told me Tile 2 has a **different** graph, so it can't be rolled up from Tile 1 (§9:327).
2. `lookml-semantics.md` §5:204 ("A declared PK that isn't unique (common when a derived table's own joins duplicate rows)… probe"). I would have trusted `sl_key primary_key: yes` and never looked inside `session_tags`, where the SELECT DISTINCT over single-key CASE columns gives ≤4 rows per session.
3. `lookml-semantics.md` §9:318 ("Fields that look the same often differ in a regex"). `event_param_page`/`page_N` use `[^\?#]+`, while `current_page_plus_N` uses `[^\?]+`. I would have shared one page-path column.
4. `lookml-semantics.md` §4:170: the pushdown-safety rule (key embeds the date) gave me a defensible cost fix for the PDT chain instead of a full-history scan.
5. `sql-review.md:271-284` + `build-notebook-agent.md:141-145` ("When Looker's own number is wrong" / tell the agent). I reproduced the `organic_search` copy-paste bug and the fan-outs instead of "fixing" them, and told the notebook agent not to dedup.
6. `liquid.md:30-31`: the dashboard default (`Device`) overrides the parameter default (`Source`).
7. `gotchas.md:50-53`: Audience Selector is listened to by Tiles 2–3 but has no effect there. The page filters aren't listened to by Tile 3.
8. `liquid.md:44-51`: `_in_query` on a filter-only field is dynamic, and `label:` Liquid is display-only (series names).
9. `build-notebook-agent.md:133-135`: "A tile's title isn't a spec". "% of Total" is a `show_dropoff` vis setting, not a percent column.
10. `gotchas.md:57-59`: the `7 day` default returns nothing on sample data.
11. `liquid.md:83-85` / `gotchas.md:134`: no Liquid/Jinja delimiters in SQL comments, and no quotes around `{{ }}`.
12. `lookml-semantics.md` §9:320: a limit without sorts uses Looker's default order (Tile 1).
13. `nested-data.md:17-20,25`: keep the `event_params` scalar subqueries, and check unqualified-name binding when moving the SQL into CTEs.
